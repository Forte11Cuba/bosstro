# Bosstro — Contributor and agent guidelines

Bosstro is a **mobile app for Mostro dispute solvers**. It brings the admin side of
[Mostrix](https://github.com/MostroP2P/mostrix) (the Rust TUI client) to a phone: see a node's
disputes, take one, chat with buyer and seller, and settle or cancel it.

It is built on the architecture of **Mostro v2** ([`app`](https://github.com/MostroP2P/app)): a
Rust core with a Flutter UI, bridged by `flutter_rust_bridge`. Bosstro is a sibling of `app`, not
a fork of it. The reference checkouts are expected next to this repository (`../app`,
`../mostrix`, `../mostro`); when unsure how something works there, read it before asserting it.

## Language

Everything in this repository is written in **English**: code, comments, identifiers, commits,
branches, PRs, issues and docs. The only exception is user-facing copy, which lives in the l10n
ARB files (`lib/l10n/app_en.arb` is the source).

## Decisions

| # | Decision |
|---|---|
| D1 | Rust core + Flutter UI. No Nostr and no cryptography in Dart. |
| D2 | Architecture comes from `app`; admin flows come from Mostrix (a behavioural reference, not code to extract). |
| D3 | The only key is the solver's key. The Mostro daemon's nsec never enters the app; *Add dispute solver* stays in Mostrix. |
| D4 | The solver's nsec is stored in `flutter_secure_storage` v10 (Android Keystore). No biometric lock for now. |
| D5 | One active node at a time, chosen with a node selector. No default node: after Log in or Create new account the solver picks theirs (Mostro first, then the trusted communities, then their own). |
| D6 | Every dispute row stores `mostro_pubkey`. |
| D7 | Screens follow Mostrix's admin flows; components and style follow `app`. |
| D8 | `app`'s design guide is the rule (`.specify/DESIGN_SYSTEM.md`, with Bosstro's amendments). |
| D9 | Onboarding: *Log in* with an nsec, or *Create new account* (generates an nsec). No 12 words — as Mostrix, which loads the solver key only as an nsec. |
| D10 | No mnemonic derivation for the solver key, so no derivation path. In Mostrix the only mnemonic-derived key is the trader identity, which must not be reused as the solver key. |
| D11 | Brand from `app`: the Mostro mascot and logo. The launcher icon is Bosstro's own emblem (`icons/bosstro.png`, the mascot as a judge), so the two apps cannot be confused on one phone. |
| D12 | Solver permissions are *Read* (take and chat) or *Read-Write* (also settle / cancel, and take over an `in-progress` dispute held by a Read solver). Bosstro learns the permission from the daemon's answers and caches it per node. |
| D13 | Serbero (the assistant Read solver) is supported: its `send-dm` messages and handoffs are read only from trusted senders. |
| A1 | License AGPL-3.0-or-later (code is copied from `app`, which is AGPL). |
| A2 | **Android is the target** the app is built for. **Linux and web** also build and run, for development and convenience, without the Android-only key protections: no screenshot blocking, no nsec copy (`PlatformCapabilities`), no QR scanning, and on the web the key sits in browser storage, much weaker than the Keystore. iOS can come later. |
| A3 | l10n: `en` and `es` for the MVP. |
| A4 | Storage per platform, as `../app`: SQLite (`sqlx`) on native, IndexedDB on the web, behind one `Storage` trait. SQLCipher is post-MVP; until then the database relies on the Android app sandbox (on Linux and the web it is not encrypted). |
| A8 | Android `applicationId` / namespace `foundation.mostro.bosstro` (it must differ from `app`'s, or one install replaces the other). |

## Architecture — the golden rule

- **Rust** (`rust/src/`): Nostr protocol, cryptography, keys, relays, persistence, business logic.
- **Dart** (`lib/`): UI, navigation, UI state, device and OS I/O (secure storage, file pickers,
  notifications).
- **No cryptography in Dart.** When in doubt: logic → Rust, device I/O → Dart.
- **Rust does not translate.** It returns data or a stable marker (`NotSolver`,
  `DisputeTakenByOther`); Dart maps it to a localized string.

### Layout

```text
lib/                 # Flutter shell — lib/features/<feature>/{screens,widgets,providers,models}
lib/core/            # theme, palettes, fonts, radii, routes — the ONLY place tokens are defined
lib/shared/widgets/  # shared components (modal, buttons, app bars, chips, data cards)
lib/shared/mascot/   # the Mostro mascot, ported from app

lib/src/rust/        # GENERATED by flutter_rust_bridge — never edit
rust/src/api/        # the bridge surface (FRB scans only crate::api)
rust/src/db/         # Storage: SQLite (native) and IndexedDB (web), one trait
rust/src/disputes/   # kind 38386: parsing, merge (NIP-01 order), the active node's feed
rust/src/mostro/     # the daemon's answers to the solver key, AdminTakeDispute, solver standing
rust/src/nostr/      # the relay pool, live subscriptions, liveness probe, event readers, transport v2
rust/migrations/     # sqlx migrations; never edit one that shipped, add a new file

icons/               # the emblem and every icon format built from it

.specify/DESIGN_SYSTEM.md
```

### Platform code

- Android-only behaviour is gated in one place, `lib/core/platform_capabilities.dart`, with pure
  functions tests can drive for every platform. A feature that needs a protection only Android has
  (FLAG_SECURE, the sensitive clipboard) is **off** elsewhere, never on without it.
- Rust that differs on the web goes behind `cfg(target_arch = "wasm32")` (`rust/Cargo.toml`,
  `rust/src/rt.rs`). Tokio's runtime and SQLite are native only; the web stores data in IndexedDB. `cargo check` does not catch wasm
  link errors; `./scripts/build-web.sh` does.

### Accepted limits

- **Web, two tabs:** the node registry reads, modifies and writes back its settings blobs
  under a per-process lock (`rust/src/api/nodes.rs`, `REGISTRY_LOCK`). On the web each tab
  is its own process over one IndexedDB database, so two tabs open at once can lose one
  tab's change (a node added or a profile refreshed). Accepted for the web (A2); ../app's
  `web_lock` (Web Locks API) is the fix if it ever matters. The dispute feed does the
  same with one dispute row (read, merge, save under `Feed::ingest_lock`); two tabs merge
  the same relay events, so at worst a revision is written twice.
- **Proof of work on the web:** mostro-core mines a request's PoW on the calling thread
  (`SingleThreadPow`). Natively the take mines on the blocking pool (`mostro::take`,
  `wrap_mined`); the web has no other thread, so the page stops while a take is mined.
  mostrod's default `pow` is 0, so today it is not felt; a node asking for a high
  `pow_first_contact` would freeze a web tab for a while.
- **A take-over of your dispute goes unseen until phase 6:** when a Read-Write solver takes
  over a dispute this key holds, the node republishes it `in-progress` and the 38386 does not
  say who holds it, so it stays in Your disputes. Settle and cancel (phase 6) learn it from
  `IsNotYourDispute` / `DisputeTakenByAdmin`.
- The key-handling limits are listed under "Key handling" (2 and 8).

### Generated code

- `lib/src/rust/`, `rust/src/frb_generated.rs` and `lib/l10n/app_localizations*.dart` are
  **generated and committed**. Never hand-edit, hand-merge or `dart format` them.
- Run `./scripts/frb-generate.sh` after **any** change under `rust/src/api/` (even a private
  item), and `flutter gen-l10n` after editing an ARB. Commit the output in the same commit as its
  cause. CI fails when they drift. `./scripts/check-generated.sh` checks it locally.
- `flutter_rust_bridge` is pinned to the **same exact version as `app`** (`2.11.1`) in
  `pubspec.yaml`, `rust/Cargo.toml` and `.github/workflows/ci.yml`; the generator refuses to run
  when they disagree. Install the CLI with
  `cargo install flutter_rust_bridge_codegen --version 2.11.1 --locked` (and `cargo-expand`).
- The app version lives in `pubspec.yaml` and `rust/Cargo.toml`; bump both together (a Rust test
  fails when they drift).

## Key handling

1. **Storage:** one secure-storage entry, `bosstro_solver_nsec`, with `flutter_secure_storage`
   v10 (Keystore-backed ciphers, not the deprecated `encryptedSharedPreferences`). One
   `FlutterSecureStorage` instance, in `lib/core/services/solver_key_service.dart`, with
   `resetOnError: false`: the plugin's default wipes the whole store when it cannot decrypt, which
   would silently delete the only key. An unreadable entry is reported and left as it is.
   **Accepted input:** a bech32 `nsec1…` or a 64-character hex secret, as Mostrix's Change Admin
   Key (`validate_nsec`); a leading `nostr:` is dropped, an `npub1…` is named as the wrong key.
   The entry keeps the key as the solver gave it.
2. **Bridge:** the nsec crosses the bridge as `Uint8List`, never as `String`; Dart overwrites
   the buffer right after the call (`_withSecretBytes`). Known limits: the Strings it comes from
   (text field, clipboard, storage plugin) are immutable in Dart and live until collected, and
   flutter_rust_bridge copies the bytes into its own message buffer, which is not wiped.
3. **Rust:** the input is held in `zeroize::Zeroizing` until it is parsed into `Keys`, then dropped.
   Rust never writes the secret to disk and never logs it. Keys live in a `SolverSlot`.
4. **Replace / log out:** unload from Rust, install the new key, and only then write storage; on
   failure reload the previous key.
5. The UI shows the npub. The nsec is shown only once on Create new account, for backup, and from
   Settings → Backup, behind a warning and a confirmation. Every screen that shows or takes the
   nsec (Log in, Create new account, Backup) sets FLAG_SECURE while it is open (`SecureWindow`):
   no screenshot, recording or recent-apps thumbnail. The nsec is never copied like an id: it goes
   through `copySecretKey` (marked `EXTRA_IS_SENSITIVE`, so Android 13+ hides the preview and
   keyboards keep it out of their history) and is cleared from the clipboard after 60 s if it is
   still there (`SensitiveClipboard`, `MainActivity.kt`). It is never selectable text either.
6. The solver key is not a trading identity: never use the nsec of `app` or Mostrix's
   `nsec_privkey` as the solver key, or both roles are linked publicly. Log in and Create new
   account say so.
7. The login screen shows the resulting npub to confirm before the first take.
8. Known limit: the Android Keystore cannot sign with secp256k1, so the key is in process memory
   while the app runs, until an external signer (NIP-46 / NIP-55) is supported.

## Protocol

- **Transport v2 only:** daemon messages are NIP-44 / signed kind 14. Nothing reads or writes
  kind 1059.
- **Disputes:** public kind 38386 events authored by the node's pubkey (`rust/src/disputes/`).
  Only a verified event of the active node with a UUID `d` and a known `s` is taken; the
  newest revision per dispute wins by NIP-01 order. The open time is the `published_at`
  tag (or the legacy `created_at` tag), never the event's `created_at`. The event carries
  no order data, so no amount before a take. Pending lists `initiated` disputes only.
- **Long-lived subscriptions** go through `nostr::live_subs` (`open` / `replace` /
  `close`), never a bare `client.subscribe` with an id or `client.unsubscribe`: it re-issues
  them on every relay that reconnects (a test enforces it).
- **Admin actions** (`mostro-core`, same version as `app`): `AdminTakeDispute` →
  `AdminTookDispute`, `AdminSettle` → `AdminSettled`, `AdminCancel` → `AdminCanceled`.
- **Dispute chat:** <https://mostro.network/protocol/dispute_chat.html>, keyed between the solver
  key and each party's trade key.
- **Attachments:** Blossom + ChaCha20-Poly1305, ported from `app`.
- **Daemon answers** (`rust/src/mostro/replies.rs`): one live kind 14 subscription per active
  node and loaded key (author = node, `#p` = solver). An answer is taken only when the node
  signed it, it opens with the key, and its `request_id` is one this process sent to that node
  with that key; a node or key change drops the old requests. A DM's content is never logged.
- **"Am I a solver on this node?"** mostrod has no read-only query. The signal is the answer to
  `AdminTakeDispute`: `CantDo(InvalidPubkey)` on an `initiated` dispute means `NotSolver` (the
  status is read again when the answer arrives); on an `in-progress` one, `CannotTakeOver`
  (ambiguous: it changes nothing). `NotAuthorized` on settle or cancel means this key is Read on
  that node. Status and permission are cached per node **and per key**. A take never sets the
  permission: mostrod gives an `in-progress` dispute back to the solver who holds it before it
  looks at permissions, so a take-over and a recovery read the same. **Never probe** another
  solver's dispute by taking it; re-taking your own is safe and is the recovery path for a lost
  answer. A take that got no answer is never retried by itself.
- **PoW of a take:** the larger of the node's `pow` and `pow_first_contact` (kind 38385):
  mostrod 0.20 drops, unanswered, a kind 14 below `pow_first_contact` from a key outside its
  spam gate, and a solver key is inside only while it holds an active dispute.
- **Auto-close:** a cooperative cancel or a seller release closes the dispute with no DM to the
  solver (38386 `seller-refunded` / `settled`); taken disputes are reconciled from 38386.
- **Serbero:** kind 14 `send-dm` messages to the solver key, read only from trusted senders, never
  treated as protocol actions.

## Style

The rule is `.specify/DESIGN_SYSTEM.md` (`app`'s guide with Bosstro's amendments in §16). Every UI
change keeps every MUST; reviews cite rule IDs (`DS-COL-1`, `DS-CMP-3`, …). The ones that bite
most often:

- No color, radius, spacing or font-size literal outside `lib/core/`; colors come from the area's
  palette (`ShellPalette`, `DisputesPalette`, `ResolutionPalette`, `SettingsPalette`).
- One accent, lime `#92D64F` with `#12161F` ink. Dispute status follows the solver's turn: lime
  when you can act, neutral otherwise. Red is for danger and errors only.
- Every text color tested at 4.5:1 in both themes (`test/core/*_contrast_test.dart`).
- Every dialog or sheet through `showMostroDialog` / `showMostroSheet`; at most one primary CTA.
- Every new screen has a widget test at 2× text, 320 dp, in Spanish, with no overflow.
- Every string from `AppLocalizations`, in en and es.

## Workflow

One PR per phase; long phases split into phased PRs. Conventional commits, branches
`type/kebab-desc`. Each PR keeps `cargo test && cargo clippy -- -D warnings`,
`flutter analyze && flutter test` and `dart tool/design_check.dart` green.

Phases: 0 scaffold · 1 solver key · 2 nodes and relays · 3 pending disputes · 4 take dispute ·
5 dispute detail and chat · 5b Serbero · 6 resolution · 7 notifications · 8 release.

Mostrix is read at tag **v0.3.8** or later.
